# 布局设计与候选比较

用于连接密集的新图，以及“线乱、绕路太多”的修改任务。位置由 Codex 结合硬件语义设计，脚本负责检查；不要将整个问题交给固定节点路由器。

## 先判断什么可以移动

固定的是硬件模块、包含关系、连接端点/方向和已知协议；图上的左右上下、框大小、接口侧边通常可以改变。保留用户明确锁定的坐标、板级方位或实际引脚排列。逻辑端口名称本身不意味着固定在某一侧。

已有 layout 是历史构图，不是硬件约束。改图先保留原文件，核对 draw.io 中手工增加的图元，不从过时嵌入 JSON 重生成并丢掉注释。

## 用连接决定邻近关系

- 先识别主通路、分支/汇聚点、共享服务者与独立子网。逻辑独立的命令/响应网络可放在单独区域；布局分区不等于新硬件父容器。
- 强关联的模块相邻。队列放在生产者与消费者之间；完成输出靠近其生产者，不能仅因“所有外部接口放左边”的形式统一，让它绕回整张图。
- 对共享资源，比较中心、两侧或上下夹置的构图。仲裁器靠近请求汇聚处，返回分派靠近接收者；TX/RX 不必相隔多列。双向关系和反馈不能被一般 DAG 排序拆得很远。
- 同构核保持重复结构；并行单元按真实共同上下游排成阵列。连接关系不足以推断新总线、仲裁器或连接点。
- 高扇出块可以拉长服务边、调整长宽比，为端口和标签留出空间。框变大应服务可读性，不表示面积或容量变化。

## 不把不同拓扑都排成一条主链

先看实际连接适合哪种形态：流水链强调共同基线；同构实例强调阵列；多方访问共享资源可让资源居中；请求与完成分派围绕同一资源时，可以把请求汇聚放上方、访问者放两侧、返回分派放下方。这样原来跨过多列的回路可能变成局部连接。

`examples/shared-hub.*.json` 展示后一种拓扑，8 条真实示例连接不交叉。它是构图候选，不是强制模板；只有本设计确实存在这些模块和连接时才采用类似布局。不要凭拓扑草图补出仲裁/响应模块。

## 联合选择位置、侧边与端点

先用短直线想象连接，尚不填密集折点。若多条连接交叉，尝试交换邻居顺序、移动共享模块、翻转支路朝向或把返回端口放到近侧。候选应改变有问题区域的相对位置，仅平移整个图或扩大画布不算重排。

主链对齐；支路排序和端点排序保持一致；连接邻近对象的侧边优先。输入不一律在左、输出不一律在右。反馈只有需要跨越主链时才绕外侧，不能把所有标记为 feedback 的连接都强制送到外围。

同侧多个连接尽量等距且居中，但服务不同通路的长模块可按功能分组。先移动相邻框、调整尺寸和端口组位置来实现直通；不能先机械 spread 再用 Z 形线补救。保持实际独立信号，不能用重线伪装成共享总线。

## 选择候选，再细化走线

复杂图至少比较两个合理构图（现有图可作基线）；只针对问题区域改变，避免为凑数量重做已清晰部分。可先用粗布局比较邻近、跨区连线与空间，再只精绘更有希望的方案。

接受顺序：

1. 所有硬件事实保留，模块不重叠，线不穿无关框。
2. 主路径、并行/共享关系一眼可读，标签与信号归属明确。
3. 尽量减少交叉、长距离重线及横跨无关区域的线。
4. 在此前提下缩短连线、减少折点，保持合适画幅和字号。

不要用单一“总折点最少”得分压倒前三项；一条短而清晰的两折路径可能优于横穿全图的直线。斜线基线与正交候选的折点数不能当成同质量比较。

`compare_layouts.py` 对相同 hardware 的两个 layout 做只读几何比较，见 [命令](commands.md)。它不会理解硬件分区、文字边界或替你选方案。比较后必须查看实际 PNG；未减少的交叉和新增的取舍照实说明。

若路由器反复出现拥挤，回到模块/侧边选择，不在同一错误构图上继续修线。完整视图仍不可读时可另补局部图，但不要把拆图作为规避重排的默认手段。
